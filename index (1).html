📦 CHAR vs VARCHAR — what's the difference?

CHAR = fixed parking spot. Even a tiny car ("Hi") occupies the whole spot. CHAR(10) always reserves 10 bytes. Perfect for fixed-length data: phone numbers, zip codes, ISO country codes, Y/N flags.

VARCHAR = valet parking — you pay only for the exact space your car needs. VARCHAR(10) storing "Hi" uses only 2 bytes + overhead. Ideal for names, emails, descriptions, variable text.

🎯 Tip from video: Use VARCHAR for almost everything unless the length is exactly identical every row. Saves storage = faster I/O, better cache efficiency. CHAR can be useful for fixed codes like MD5 hashes or session tokens.

🔢 INTEGER vs NUMERIC — when to choose?

INTEGER → whole numbers only. Use for: age, product quantity, students count, auto-increment IDs. Why? Integers are blazing fast — CPUs love them, indexes stay lean.

NUMERIC / DECIMAL → exact decimal math. Use for: money (PHP, USD, EUR), percentages, precise measurements. Never use FLOAT for currency — rounding errors can break financial logic!

⚡ Performance rule: If you don’t need decimals, pick INTEGER. It’s like a sports car vs a heavy truck — leaner storage = quicker aggregations and joins.

🔗 UNION vs UNION ALL — key difference?

UNION → merges two result sets and removes duplicate rows. It performs an implicit sort / distinct operation — like checking every ID card in a crowd. Useful when duplicates would mislead analysis.

UNION ALL → just stacks results, keeping all rows including duplicates. No duplicate elimination overhead → much faster, especially on large tables.

🚀 Optimization secret: Prefer UNION ALL unless you critically need to remove duplicates. UNION can be 2-3x slower because of the sorting + deduplication step. Don’t waste CPU cycles on unnecessary distinct checks.

⚙️ DISTINCT, LIMIT, != , <> — what's good about them?

  • DISTINCT – removes duplicate rows. Great for "unique cities list", but caution: can be heavy on wide tables; it forces sorting or hashing.
  • LIMIT – returns only first N rows. Life saver for performance — prevents scanning millions of rows if you need only previews. Always use during development/testing.
  • != – "not equal to". Example: WHERE price != 0. Handy for exclusion filters.
  • <> – exactly the same as !=. Some SQL flavors prefer <> (standard SQL), others accept both. Identical meaning: “not equal”.
⚠️ Critical insight: LIMIT is your best friend for speed — always consider pagination. But watch out: != and <> often break index usage, leading to full table scans. Avoid them on huge tables if possible; use positive filters (e.g., status = 'active' instead of status != 'archived') when you can.

Pro tip: Combine LIMIT with ORDER BY to get predictable, lightning-fast result slices.
